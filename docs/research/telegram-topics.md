# Telegram topics：问题、处理方式与边界

更新：2026-10-16。记录当前原型实际遇到的问题；产品行为以 Telegram 和历史投递设计为准。

## 入口与消息归属

| 问题 | 原因或平台边界 | 当前处理 |
| --- | --- | --- |
| `/start` 后多出会话 | Telegram 私聊自动创建话题和产品新建 session 是两回事；若允许客户端自行创建 topic，默认入口会混乱 | BotFather 开启私聊 topics，关闭用户自动建话题；启动检测配置并提示日志；`/start` 只打开管理菜单，不创建 Codex thread |
| 看不到 topic | bot 必须启用私聊 Topics；历史清空也可能只隐藏客户端记录 | 检测 capability；不靠旧消息是否可编辑判断菜单可见；每次主动打开都发送新菜单 |
| 清空聊天后 `/start` 无反应 | 编辑旧菜单即使成功，客户端也未必再次显示旧消息 | 新菜单回应；固定管理 topic 的创建通过账本去重；只有明确不存在才重建 |
| 普通消息误发给选中的 session | “当前选中会话”不能跨 topic 作为隐式发送目标 | 管理 topic 永不绑定原生 session，拒绝任务正文；topic 外操作转入管理 topic，并在原位置提示；只有已绑定的 session topic 接受任务 |
| 外部输入看不到 | 之前普通观察只过滤出 agent 文本 | 同一原生会话中 Desktop/CLI 等输入用 🧑‍💻 展示；工具和推理不转发；不合并别的 session |
| 自己输入重复出现 | Telegram 原消息与原生 userMessage 是同一输入的两个表示 | 用持久操作账本对应的 `client_user_message_id` 精确去重，按 bot、私聊、provider、thread 隔离；不按正文相同猜测来源 |

Bot API 不能把用户已发送的消息真正“移动”进另一个 topic。转入管理的含义是路由处理与回复，而非伪造用户消息移动。原生服务若不保留客户端消息 ID，无法可靠识别该条输入来自哪个客户端；宁可显示未确认来源的输入，也不按内容相似度隐藏真正的新消息。

## 菜单与目录

| 问题 | 当前处理 |
| --- | --- |
| 按钮过长、列表有占位项、选择时按钮过期 | 管理菜单使用 Markdown + 实际条目编号；用户每次操作产生新菜单；不填满空行或虚构条目；选择绑定稳定 ID |
| 配置轻微变化使菜单失效 | 权限范围变化仍重新确认；速率、显示设置和工作区活动时间变化不使授权失效；旧菜单回复重新打开相应页面 |
| `tg.workspace.page` 显示成界面文字 | 它是内部翻译 ID，预期显示“已登记 N 项 · 当前 X–Y”；旧 release 没有因 YAML 变动重新编译资源。增加编译依赖，并比较每个 ID 的编译结果与语言文件 |
| 缺少 cpet-proposal，没有下一页 | 工作区来自 catalog 和原生会话 cwd，非目录扫描。完整读取活跃、普通、归档会话各页；工作区每页八项，可翻页；新目录可 `/add` |
| 列表排序不直观 | 工作区按所属会话最大 `updatedAt` 倒序，无时间者最后；会话汇总 cwd 和登记 worktree 的各页后整体倒序。会话后续页读取固定快照，避免新活动导致重复或跳项 |
| 同名 workspace 选错主机 | `/new` 按 host → workspace → 标题 → 确认；内部绑定完整 ID；快捷入口可用 `HOST/WORKSPACE`，有歧义时拒绝猜测 |

工作区时间来自原生会话元数据，后台扫描和已绑定会话观察更新；它不是文件修改时间。未绑定的外部活动到下一次发现或主动 `/refresh` 才反映。会话列表快照最多保留一小时、64 份；过期重新展示首页。时间相同用稳定字段排序。

## 标题、图标与运行反馈

| 问题 | 当前处理 |
| --- | --- |
| 标题出现“空闲”“待继续”、路径太长 | 标题只保留原始名称，按 grapheme 和平台字符数截断；详细信息 `/status` |
| 📁 / 💬 重复、状态图标叠加 | 管理 topic 用原生 📁；会话用原生状态 icon；标题不再重复拼 emoji；icon 和标题分开更新 |
| icon 修改太频繁 | 只在状态变化时更新，短时间合并；共享私聊和 bot 速率预算；不用它做动画；Telegram 可能产生服务提示 |
| 新建后标题被当作第一轮任务 | 创建 thread、必要时补标题，但不自动发送 turn；等待用户的首条任务 |
| “开始新一轮”等 ACK 刷屏 | 正常成功不单发 ACK；细节写入 tracing；运行时通过独立 typing lease 续期 |
| 过程和最终结果难区分 | 原生 phase 对应 💭 commentary/partial/plan、✅ final_answer；缺 phase 为 💬，不猜成最终结果 |
| “连接未知”反复出现 | 运行状态与历史可读性分开；同一次故障只提示一次 ❌；成功读取后解除故障标记；未知写结果不自动重发 |

## 历史、附件与错误

`/history` 动态读取原生历史，选最新用户输入及其后同一 turn 的 final_answer；不含 commentary/工具/推理，且不把 steer 之前的旧 final 当作本次回答。当前输入所在轮失败时展示 ❌；Codex 明确将重试的通知展示 ⚠️，表示服务端重试，不是 PocketPilot 重发任务。

cpet-proposal 最新会话的只读检查发现原生错误记录，但它在较早轮次，最近用户输入所在轮没有错误。默认历史会提示有较早错误；`/history errors` 独立显示最近十条错误及 turn ID，不把旧错误放到新输入下面。轮次的 `error.message`、失败/中断状态及连接上收到的 error 通知进入展示；错误补充诊断字段不直接转发。已观察错误按 provider/thread 留在桥接数据库，重启后可查询；原生服务未持久化且桥接从未收到的历史通知无法补回。

原生 Desktop 附件包装只用于展示时清理：保留 `My request` 正文，附件变为 📎 文件名，移除本地绝对路径及包装提示；普通讨论附件格式的文本不误删。原始模型输入不改写；不读取、下载或预览图片。Telegram 上传附件明确提示当前只转发 caption 的文字说明；无 caption 时不启动任务。消息链接关闭预览，避免隐式图片预览。

进入活跃会话发送一份可读取历史集合，超长作为 Markdown 文档；普通输出短时合并并限速。观察游标包含 item 内容和 phase，phase 从过程变 final、正文不变时也显示最终结果；旧版正文 hash 升级不重播已知文本。

## 删除与同步的限制

Bot API 没有列出当前 topics 或读取单个 topic 的接口，也没有可靠的 topic-deleted 更新。因此 `/topics` 只能管理账本记录的 topics。使用无内容的元数据检查和发送结果发现明确的 missing-topic；超时、429、closed 不等于已删除，不盲目重建。

单个删除和 `/topics clear` 都先确认；批量确认保存具体 ID 范围，排除管理 topic 和确认后新增的 topic。只删除 Telegram topic、消息及本地关联，保留原生会话。删除结果未知时暂停对应投递，不自动重试；用户复核后重新确认。删除后可重新添加同一原生 session 为新 topic。程序从未记录的 topics 无法批量发现和清理。

命令菜单范围是整个私聊，不能按 topic 注册不同列表；`/help` 按上下文解释可用命令。管理操作、删除和连接恢复都不得停止原生任务；观察不调用 resume，续轮只在明确用户输入时发生。

## 验证方式

自动化覆盖菜单分页与翻译、按活动时间排序、跨路径会话排序与稳定翻页、外部用户输入、Telegram 自身输入去重、附件清理与 caption、phase 变化、历史错误归属、错误留存、旧游标升级、故障提示去重，以及现有的配对/删除/未知结果/typing 生命周期约束。真实 cpet 检查只读取列表及历史，未发送任务、resume 或停止请求。

接口边界参见 [Telegram 设计](../design/telegram.md) 中的官方资料。真实 Telegram 客户端呈现仍需用户手工复核。
